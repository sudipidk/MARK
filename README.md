# MARK Discord Bot

MARK is a general-purpose Discord bot. Commands are loaded from individual JavaScript files in `commands/`; reusable logic is in `services/`.

## Setup

1. Install dependencies with `npm install`.
2. Configure `TOKEN`, `CLIENT_ID`, and `MONGODB_URI` in the environment (or a local `.env` file). On Railway, set these under the bot service's **Variables**; a Railway MongoDB service's `MONGO_URL` variable is also accepted as a connection-string fallback. The URI must point to a MongoDB deployment accessible to the bot. Slash commands deploy globally; optionally set `GUILD_ID` to also register the same commands in a test server for immediate testing. Discord may take time to propagate global command updates.
3. Enable the **Message Content Intent** and **Server Members Intent** in the Discord Developer Portal. Message content is used by counting; the members intent supports accurate member cache information and active-timeout listings. Hall of Fame/Shame also listens for server reactions using the Gateway Guild Message Reactions intent.
4. Invite MARK with only the permissions needed for the features you use. These include View Channels/Send Messages/Embed Links for embeds and logs; Add Reactions/Manage Messages for counting and Channel Control message deletion; Kick Members, Ban Members, and Moderate Members for moderation and configured Channel Control timeouts; and Read Message History for timeout listing, Wordle, and reaction-based halls. Channel Control administrators need Manage Channels or Administrator. The existing Message Content and Server Members intents are used; enable them in the Discord Developer Portal as documented above.
5. If you have existing counting data in `data/counting.json`, run `npm run migrate:counting` once before starting the bot. The migration is safe to rerun and preserves any counting records already in MongoDB. Then register commands with `npm run deploy` and run `npm start`. Run `npm test` to execute the automated checks.

## Phase 1 commands

- Profiles and bot information: `/userinfo [user]`, `/serverinfo`, `/avatar [user]`, `/uptime`
- Moderation: `/kick`, `/ban`, `/unban`, `/timeout`, `/untimeout`, `/bans`, `/timeoutes`
- Channel Control: `/channelconfig gif|emoji|media|sticker|text channel:<channel> enabled:<true|false>`, `/channelconfig all|view|disable|reset channel:<channel>`, `/channelconfig delete channel:<channel> enabled:<true|false>`, `/channelconfig timeout channel:<channel> enabled:<true|false> [duration:<duration>]`, and `/channelconfig threshold channel:<channel> violations:<1-1000>`
- Moderation logs: `/modlog setchannel`, `/modlog disable`, `/modlog config`
- Suggestions: `/suggest`, `/suggestion setchannel`, `/suggestion disable`, `/suggestion config`, `/suggestion view`, `/suggestion list`, `/suggestion stats`
- Hall of Fame/Shame: `/hof setemoji|setchannel|setnum` and `/hos setemoji|setchannel|setnum` configure each hall's reaction emoji, destination, and minimum count. When a user's message reaches the configured count, MARK posts an embed with their username, avatar, message, and first image (if present). Configuration requires Manage Server or Administrator.
- Counting remains available through the existing `/counting-*` commands.

## Phase 2 commands

- AFK: `/afk [reason]` and `m!afk [reason]`. AFK state is server-specific, persisted in MongoDB, and clears when the member sends a non-command message.
- Reminders: `/remind <duration> <message>` and `m!remind <duration> <message>`, `/reminders`, and `/reminder cancel <id>` (also `m!reminders` and `m!reminder cancel <id>`). Durations accept seconds, minutes, hours, days, and weeks (including combinations) up to 365 days. Reminder DMs require the member to allow DMs from the server.

Suggestion IDs and votes persist in JSON. Users may change a pending suggestion vote; each user has one upvote or downvote per suggestion. Approval/denial requires Manage Server or Administrator and a reason via modal. After a decision, voting and further decisions are disabled.

Moderation log entries are emitted for moderation actions MARK performs through its commands. Actions taken manually in Discord or by another bot are not monitored through audit-log events.

Channel Control stores per-channel settings in MongoDB collections `channel_configs` and `channel_violations`. It starts with all content categories allowed, automatic deletion enabled, and timeouts disabled. `/channelconfig disable` pauses enforcement while preserving settings; a content-setting command reactivates enforcement while changing only the selected category, and `/channelconfig all` reactivates the system with all content categories allowed without changing moderation settings. `/channelconfig reset` deletes settings and violation counts. Violations reset one hour after the latest violation by default; timeout durations are limited to 28 days. Exempt roles and users are supported by the stored configuration but do not currently have public management subcommands.

## Social and fun commands

The permanent global entertainment tests are `/dnatest [user]`, `/gaytest [user]`, `/iqtest [user]`, `/lovetest user1 user2`, `/rizztest [user]`, and `/lucktest [user]`. Their prefix forms are `m!dnatest [@user]`, `m!gaytest [@user]`, `m!iqtest [@user]`, `m!lovetest @user1 @user2`, `m!rizztest [@user]`, and `m!lucktest [@user]`. Results are keyed by Discord user IDs, never server IDs or usernames. DNA's Gay, Rizz, and Luck traits read the same saved results as their individual tests. DNA and IQ scores are fictional entertainment only; they are not scientific or clinical assessments.

`/chatest [user]` and `m!chatest [@user]` show the user's stable global character assignment. `/charoll [user]` and `m!charoll [@user]` create a first assignment or reroll after the global 24-hour cooldown. A successful assignment starts a new 24-hour cooldown; concurrent requests cannot produce multiple rerolls. The cooldown and selected message persist in MongoDB across servers and restarts.

Social commands are `/roast user`, `/compliment user`, `/kill user`, and `/kiss user`, with matching `m!roast @user`, `m!compliment @user`, `m!kill @user`, and `m!kiss @user` forms. These choose a weighted outcome and a random message for each invocation. Responses remain fictional, playful, and non-explicit.

`/help` includes all of the tests, character, and social commands, and shows the matching `m!` forms where available. `/characters [page]` lists the character catalogue by name and source only; it intentionally does not display character messages.

Edit `data/chatest.json` to add or change characters: each entry needs a unique lowercase `id`, `name`, optional `source`, `enabled` boolean, and one or more `messages`. Set `enabled` to `false` to exclude a character from future assignments; existing assignments remain unchanged. Add new traits by editing `data/dna-traits.json` with a stable `id`, display `name`, and `max`; existing profiles receive only missing trait IDs. `sharedScore` is reserved for the existing shared scores `gay`, `rizz`, and `luck`.

Edit `data/roast.json`, `data/compliment.json`, `data/kill.json`, and `data/kiss.json` to expand social message categories. Each outcome has an `id`, integer `weight`, and a `messages` array; outcome weights must total exactly 100. Each invocation chooses a weighted category first, then a message within it. Invalid social libraries are logged and use a small safe fallback. Supported placeholders are `{author}`, `{target}`, `{authorName}`, and `{targetName}`. Score descriptions are editable in `data/rizz.json`, `data/luck.json`, and `data/iq-bands.json`; saved scores do not change when descriptions are edited. Love-test messages are in `data/lovetest.json`; a pair's selected category and message are saved with its score.

Fun data uses the shared `MARK` MongoDB database and initializes unique indexes for global scores, DNA profiles, and character assignments at startup. Deploy the added slash commands with `npm run deploy`; deployment remains global, with the optional `GUILD_ID` mirror available for testing. Repository `data/` JSON catalogues are bundled with the app and do not require a writable Railway volume.

## Wordle

Wordle runs independently in each server. An owner or Wordle admin must first configure the dedicated channel with `/wordle set-channel`; MARK checks View Channel, Send Messages, Embed Links, and Read Message History permissions, then starts the first challenge. Players submit guesses by replying to the announcement or any tracked MARK feedback message. Each player gets a separate attempt history; feedback tiles are public.

Admins use `/wordle admin user` (server owner only) to toggle Wordle admin access; `/wordle create` or `/wordle queue-add` to add dictionary-backed custom challenges; `/wordle queue`, `/wordle queue-remove`, `/wordle queue-move`, `/wordle queue-edit`, and `/wordle queue-clear` to manage the pending queue; and `/wordle skip`, `/wordle end`, `/wordle reveal`, `/wordle settings`, or `/wordle admin stats` for administration. Active answers are not shown in queue or active-challenge views. Players can use `/wordle stats`, `/wordle leaderboard`, and `/wordle history`.

The curated dictionary is `data/wordle-words.json`, with exactly 100 automatic answers for each supported length (5, 6, and 7 letters), plus extra dictionary entries for custom answers. Guesses may be any alphabetic word as long as it matches the answer's length. Automatic length weights default to 70/20/10 and rewards to 5,000/7,500/10,000 MARK; the settings command permits reward changes but rejects automatic rewards below 5,000. Custom answers can be 1–15 letters when present in the curated dictionary. Custom challenges are queued behind the current game and take precedence over the next automatic challenge.

Wordle stores per-server settings, challenges/archives, player attempts, and statistics in `wordleSettings`, `wordleChallenges`, `wordlePlayers`, and `wordleStats` in the existing `MARK` database. Hall settings and repost deduplication are stored in the `hallSettings` and `hallPosts` collections. Prize credits use MARK's existing global economy account and transaction ledger with a challenge-specific idempotency key. As with other MARK economy operations, MongoDB transactions require a replica set (MongoDB Atlas supports this). No additional environment variables or packages are required. Deploy commands with `npm run deploy`; the bot needs the existing Message Content Intent and Read Message History in the configured Wordle channel, plus the Guild Message Reactions intent for the hall features.

## Persistent storage

Counting configuration and statistics are stored in the MongoDB `MARK.counting` collection, with one document per Discord server. AFK state and reminders persist in the `MARK.afk` and `MARK.reminders` collections. Reminder deliveries are atomically claimed to prevent duplicate delivery; if the process restarts during a DM attempt, the reminder is marked failed because Discord does not provide a transaction with MongoDB to safely retry that uncertain delivery. Legacy counting JSON is imported with `npm run migrate:counting`. Moderation configuration, suggestions, and other JSON data are written to `data/` by default; set `BOT_DATA_DIR` to a writable persistent directory in production for those features. `COUNTING_DATA_DIR` remains supported as the legacy JSON import directory when `BOT_DATA_DIR` is not set.

Channel Control uses the existing `MARK` MongoDB connection. `channel_configs` has a unique `{ guildId, channelId }` index; `channel_violations` has a unique `{ guildId, channelId, userId }` index and a TTL index on `expiresAt`. The application checks each violation expiry itself as well as using MongoDB TTL cleanup. Deploy `/channelconfig` with the existing `npm run deploy` command; no additional Railway variables, services, or packages are required.

## Economy

The economy is global across every Discord server where MARK is installed. A player's Discord user ID is the account identity, so balances, inventory, titles and Variant codes, cooldowns, active effects, statistics, transaction history, and limited-stock purchase limits are shared across guilds. `/richest` and `/economy` report global data. Lottery rounds and entries remain guild-specific games, but their payouts update the same global accounts. Transaction records retain the originating guild for provenance.

Economy data uses the existing MongoDB connection and initializes indexes at startup. Accounts, append-only transaction records, operation idempotency results, inventory, title ownership, active effects, weekly stock, and daily lottery rounds are persisted in the `economy*` collections. On first startup after the global-account upgrade, legacy per-guild player records are archived in `economyLegacyArchive` and migrated once. Wallet balances and inventory quantities are summed across guild records to preserve recorded value; this may retain duplicated historical starting grants. Cooldowns keep the latest timestamp, titles are unioned, unique Variant codes are preserved, and active Luck durations are combined by tier. If equipped titles conflict, the title from the lexicographically smallest source guild is kept (an existing global account's equipped title takes precedence). Current-period limited stock carries over into one global allocation; older stock history is archived. The migration is transactional per user and is not marked complete until player and stock migration finishes.

Balance-changing multi-document actions require MongoDB transactions; deploy against a replica set (MongoDB Atlas supports this). If transactions are unavailable, economy writes fail rather than partially applying a debit or credit.

Economy commands include `/bal`, `/daily`, `/weekly`, `/give`, `/steal`, `/cf`, `/lottery`, `/richest`, `/work`, `/beg`, `/profile`, `/economy`, `/transactions`, `/cooldown`, `/shop`, `/inventory`, `/item`, `/use`, `/boosts`, `/titles`, `/bank`, `/bankfunds`, `/deposit`, `/withdraw`, `/achievements`, and `/help`. The restricted admin commands are `/addmoney`, `/removemoney`, `/setmoney`, `/reset`, and `/resetall`. Normal player-facing economy replies are public embeds; transaction history remains private. Coinflip wagers use `/cf choice:<Heads|Tails> amount:<coins>` with any positive whole-number wager affordable from the wallet. Currency amounts accept whole coins or compact values such as `1.5k` where the command takes a string amount. Discord requires commands with subcommands, so shop browsing is `/shop all page:<N>`, title browsing is `/shop titles page:<N>`, and title listing is `/titles list`; buying/selling use `/shop buy item:<ID>` and `/shop sell item:<ID>` (with optional quantity for stackable items).

Bank deposits require a two-step `/deposit`: the first invocation previews principal, the 2% fee, and total wallet deduction; confirm with the returned token within five minutes. Deposit fees are rounded down to whole coins. Each confirmed deposit is an individual 12-hour lot. `/lottery number:<1-10> amount:<coins>` resolves each new wager immediately with three distinct crypto-random numbers; legacy shared rounds remain available only to settle historical rounds already open. `Ones Above All` retains the former Avenger price of 25,000,000 coins; existing ownership migrates without discarding historical transaction records.

Tuning values and reward ranges are centralized in `services/economy-config.js`; title and consumable details live in `services/economy-catalog.js`. Daily lottery rounds and the bank deposit limit use Nepal Time; weekly limited stock restocks Monday at midnight Nepal Time. Register the slash commands with `npm run deploy` after deployment.
